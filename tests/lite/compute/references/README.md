# Independent shaping evidence

These files are test-tooling evidence, not runtime engines or product modes.
Tests consume the checked-in JSON without HarfBuzz installed. No expected record
is derived from Lite shaping output.

## Regeneration

With the existing Node 22 and pinned tools (no dependency installation):

```sh
node scripts/generate-shaping-references.mjs --write
node scripts/generate-shaping-references.mjs --check
```

`--check` regenerates in memory, checking byte identity, including source hashes;
it reuses only the original generation timestamp. The large `existing-impact-report.json`
and `.md` are **diagnostic, not committed**. Their regenerated bytes are checked against
`existingImpactReportSha256` and `existingImpactReportMarkdownSha256` in the persisted
`reference-identity.json`, which is itself byte-checked. They need not exist on disk
for `--check`; all other generated outputs, including compact/audit identity bindings,
remain byte-checked. `--write` still writes both diagnostics locally along with the
committed generated files. To demonstrate fail-closed identity checking:

```sh
node scripts/generate-shaping-references.mjs --check --expected-binary-sha256=wrong
```

That command must fail before shaping or writing anything. Tool hashes, font
hashes, configuration and generator-source hashes are recorded in
`reference-identity.json`. Any intended reference change requires review.

their font hashes, old adapter outputs and independently agreed HarfBuzz outputs.

yAdvance; later contextual records act on the sequence modified by earlier actions,
with skip-aware positions and no extra contextual cluster merge. The raw synthetic
font hashes and record data remain identical; annotations and identity metadata
have changed, so the entire synthetic JSON is not claimed byte-identical.

## R3: attached advances and a fail-closed evidence gate

For all profiles, the approved contract zeroes advances only on glyphs actually
attached by MarkBase, MarkMark or MarkLig, after GPOS and before propagation.
Unattached glyphs retain GPOS-adjusted font advances regardless of GDEF class.
This is not HarfBuzz's GDEF-wide mark-width zeroing.

Exactly three legacy MarkMark rows use `A-attach`: all six fields are derived
from old independent records, font hmtx and the C1 pen-relative transform.
Every attached glyph's root-relative absolute position must equal HarfBuzz
exactly; only explicitly computed unattached-mark advance differences and their
downstream translations may differ. No Lite output supplies expected fields.

`phase1-gate-results.json` records both mandatory guards and every residual ID.
The Devanagari guard passes: glyphs 149–154 do not occur in its references.
The H guard remains unchanged and passes all 1529 HarfBuzz-positioned rows.

The six previously quarantined legacy rows have individually reviewed,
font-intrinsic position proofs, not a general H exemption:

- Exactly three `N-proof` rows prove no GSUB effect and no MarkLig attachment.
  Their nominal cmap/cluster/hmtx/zero-offset records equal the old records
  exactly. HarfBuzz differs only by zero advances on unattached class-3 glyphs.
- Exactly three `G0` rows prove there is no GPOS table. HarfBuzz supplies the
  reviewed GSUB stream and C7 clusters, checked against an independently proved
  ligature span. Every advance is hmtx and every offset is zero. HarfBuzz may
  differ only by class-3 advance zero and xOffset minus hmtx.
- No other IDs may use these proofs. All six fields are checked, and any other
  difference fails. The original A-attach fixture's strict assumptions remain.
